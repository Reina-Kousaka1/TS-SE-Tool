## Current architecture

- C# / .NET 10 remains the application and savegame foundation. The existing `TSSE.Core`, `TSSE.Savegames`, `TSSE.GameAdapters`, `TSSE.Analytics`, and status-only `TSSE.Bridge` projects remain in the solution.
- `desktop/TSSE.Desktop` is the native desktop application, built with Avalonia 12.2.0, MVVM, Microsoft dependency injection, and a central Fluent theme with dark and light variants.
- The app contains navigation and interface previews for Command Center, Savegame Explorer, Vehicle Studio, Economy Intelligence, Savegame Time Machine, Compatibility Lab, Diagnostics Center, and Settings. Search filters the sections; vehicle category and analytics-window controls change preview state.
- Dark/light theme selection is now remembered in a small local preference file. The window reports when the preference could not be read or saved; this setting stores no game or savegame data.
- The interface ships embedded English and German text resources. It follows the operating-system UI culture at startup and falls back to English for other cultures; Settings shows the resolved language. A language change requires restarting the app.
- Screens show only current foundation facts and explicit empty states. There are no sample balances, vehicles, profiles, snapshots, game diagnoses, or fabricated events.
- No profile scanning or real game-save reading is enabled. Save writes, restore actions, and background profile monitoring are disabled.
- Electron, Phoenix, Elixir, JavaScript UI assets, and TypeScript are not part of the new target architecture.

## Retained foundation and savegame safety

The SII syntax document and atomic file transaction remain intact. The parser preserves source text and supports a narrow update to an existing unique field; it does not implement complete SII semantics, compressed save containers, or game-version schemas. The transaction snapshots caller-supplied bytes, validates and stages that same stable private snapshot, checks the original SHA-256, retains a backup, and reports uncertain outcomes as `RecoveryRequired`.

`GameAdapterRegistry` starts empty. No game or save version is verified for reading or writing, so the UI cannot open or edit a production profile. The analytics library keeps recorded transactions distinct from snapshot-derived balance differences; it has no profile-backed history in the desktop app. Snapshot deltas require a stable `ProfileId`; older local snapshots without one remain readable but are excluded from delta calculations. Callers must also scope transaction inputs to one profile because transaction records do not carry profile identity.

The parser has only synthetic fixtures. The referenced [PR #147](https://github.com/LIPtoH/TS-SE-Tool/pull/147) reports local roundtrips over 21 ATS v97 saves, but its 64 changed files include no save-format fixtures, so that result cannot be reproduced from the PR. [PR #149](https://github.com/LIPtoH/TS-SE-Tool/pull/149) describes an ETS2 1.61 compatibility update and says ATS was not tested; its 1,318 changed files also include no save-format fixtures. Neither report is treated as compatibility evidence for this foundation, and no code was copied from them. Genuine ETS2/ATS saves, mods, Coaches DLC, unknown-field roundtrips, and complete serializer behavior remain unverified. A successful generic atomic transaction is not evidence of a safe game-save edit.

## Architecture self-review — atomic payload snapshot (2026-11-26)

No separate Architect tool was available, so this is the implementation agent's self-review and not an independent review. Inspection showed that `ReadOnlyMemory<byte>` can wrap caller-mutable storage: the validator and file writer previously received views over the same buffer, allowing a caller mutation after validation to change the bytes being committed. `AtomicFileTransaction` now makes a bounded private copy before validation and uses that exact copy for validation, staging, and both hash checks. The regression test mutates the caller buffer inside the validator and asserts that only the bytes approved by the validator reach the target.

Evidence: the source-linked .NET 8 transaction harness passed this mutation scenario; the existing expected-original hash, staged-content validation, backup, recovery, and size limits remain in the production code. CI run [45724333605](https://github.com/Reina-Kousaka1/TS-SE-Tool/actions/runs/45724333605) passed the expanded 8-test Core suite and all other tests across five automatic targets. The copy adds at most 128 MiB transient memory within the existing payload limit. The transaction remains disconnected from live profiles, and desktop save writes remain disabled.

## Architecture self-review — native Fedora RPM verification (2026-11-26)

No separate Architect tool was available, so this is the implementation agent's self-review, not an independent review. The current Linux package verifier installs RPMs on Ubuntu with `rpm --nodeps`; this checks RPM metadata and launcher behavior, but cannot establish that Fedora's dependency resolver accepts the declared `Requires`. Fedora Linux 45 is the current stable release as of this review ([Fedora release announcement](https://fedoramagazine.org/announcing-fedora-linux-45/)). GitHub Actions supports job containers on Ubuntu runners ([container jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/run-jobs-in-a-container)) and provides native x64 and ARM64 Linux runner labels ([runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)).

Decision: add isolated Fedora 45 CI jobs on matching x64 and ARM64 hosts. Build the RPM in that environment, install it with DNF dependency resolution enabled, launch the installed wrapper under Xvfb, then remove it. DNF must allow the unsigned temporary local package because Phase 2 does not sign packages; this check does not validate package signatures. The jobs do not publish artifacts or touch user data. Keep the existing Ubuntu package checks as separate evidence for DEB and RPM metadata/install/remove behavior.

Review evidence and outcome: the first run [45731735310](https://github.com/Reina-Kousaka1/TS-SE-Tool/actions/runs/45731735310) failed on both architectures while RPM 6 attempted to generate a debugsource subpackage from the self-contained publish tree; `libHarfBuzzSharp.so` and `libSkiaSharp.so` have no debug symbols and no source files are packaged. The RPM 6 build documentation exposes `%_enable_debug_packages` as the debug-package generation switch ([RPM build process](https://rpm.org/docs/6.0.x/manual/buildprocess.html)). The self-review therefore sets `_enable_debug_packages` to `0` in this binary-only package spec, without changing payload validation, declared runtime dependencies, test execution, or DNF's dependency resolution. Run [45732305189](https://github.com/Reina-Kousaka1/TS-SE-Tool/actions/runs/45732305189) on `20c6bae` passed the full 43-test .NET 10 suite on Fedora x86_64 and aarch64, self-contained publish, RPM build, DNF dependency resolution, installed app launch under Xvfb, and removal on both architectures. The same run passed the five desktop targets, including Linux DEB/RPM checks. Both Fedora jobs used the same pinned Fedora 45 multi-architecture image digest.

Limits: the local package is installed with `--nogpgcheck` because no signing key is supplied; signatures and production repository trust are not tested. This is an implementation-agent self-review, not an independent review. The result establishes Fedora 45 package/runtime behavior in the CI container, not a Fedora workstation, Wayland, upgrade, or clean-user install. No savegame access or write operation is part of this check.
